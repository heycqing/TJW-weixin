# 从随机匹配到第一版可用算法：一次微信匹配服务的修补记录

## Trigger

这次动手的起点不是“想做一个多聪明的推荐系统”，而是一个很朴素、也很危险的问题：匹配逻辑里先随机查一个候选人，再分别更新双方的匹配关系。

在低并发时它看起来能工作；但只要两个用户同时进来，就可能抢到同一个候选人。于是数据库里会出现三角关系：A 以为自己匹配了 C，B 也以为自己匹配了 C，而 C 只会被最后一次写入覆盖。这种 bug 不一定每天出现，但一旦出现就会直接破坏用户体验。

顺着这个问题继续看下去，旧逻辑还有几个明显短板：

- 机器人和真实用户被一视同仁随机抽取。
- 5 个问答文本已经存在数据库里，却完全没有进入匹配。
- 同一个机器人可以被同一个真实用户反复遇到。
- 没有历史配对记录，无法排除重复，也没法为后续数据分析做准备。

所以这次的目标被压缩成一个第一版：先不要做复杂推荐系统，先把匹配从“随机抽卡”整理成“过滤、打分、抢占、记录”的小闭环。

## Investigation

代码里的关键路径很集中：用户上传照片后，服务按目标性别随机查一个用户，然后并行更新：

- 当前用户的照片
- 当前用户的 `needOpenId`
- 候选人的 `needOpenId`
- 当前用户的流程状态

这个形状的最大问题是“查”和“写”之间没有锁，也没有事务语义。候选人被查出来之后，任何并发请求都可能在更新前抢走它。

第一反应是用 D1 的事务能力把几条语句包起来。但这里有个细节：第二步更新依赖第一步选出来的候选人。如果只是把“先查再改”原样放进批量执行，仍然很容易写出不够紧的逻辑。

最后采用的方案是：先查询一批候选并在应用层打分，然后对具体候选执行一次带条件的 `UPDATE ... RETURNING`。这条更新只有在“当前用户和候选人都仍未被占用”时才会同时写入两行。如果返回行数不是 2，就说明抢占失败，继续尝试下一个候选。

这样保留了算法灵活性，又把最终绑定动作收紧到了数据库条件更新上。

## Key Changes

第一版匹配流程被整理成四步：

```text
候选过滤 -> 候选打分 -> Top N 随机探索 -> 条件抢占并记录历史
```

候选过滤先做硬约束：

```text
性别/取向匹配
有照片
不是自己
当前没有被别人占用
历史上没有和当前用户配过
```

然后打一个非常克制的第一版分数：

```text
真人基础分：+100
答案关键词每重叠一个：+10
活跃小时相同：+10
活跃小时相差 1-2 小时：+5
机器人：不加真人基础分
```

这里有一个刻意选择：真人优先不是纯软分数，而是硬策略。只要真实用户候选存在，就不进入机器人池。机器人只承担兜底作用，避免“没人可匹配”时流程直接断掉。

为了避免分数最高的人被机械地反复消耗，算法不是永远取第一名，而是取前 5 名再随机尝试。这保留了一点探索性，也让产品仍然有“邂逅”的感觉。

数据库层新增了两类信息：

```sql
activeHour INTEGER
```

用于记录用户最近活跃小时。

```sql
match_history (
  userOpenId,
  matchedOpenId,
  createdAt,
  accepted
)
```

用于记录双向匹配历史。当前第一版先用它排除重复；以后可以继续扩展成漏斗分析、接受率分析、机器人消耗统计。

还有一个很现实的限制被保留下来了：现有产品流程是“先上传照片并匹配，再回答问题”。这意味着新用户第一次匹配时，系统还没有他的 5 个答案。第一版算法因此做了降级：有历史答案就参与关键词评分；没有答案时仍然能用真人优先、历史排除和活跃时间。

如果以后要让问答真正成为匹配核心，流程本身要改成“先答题，再匹配”。

## Verification

这次自检分了三层：

1. 单元测试覆盖签名校验、XML 解析、基础回复、匹配评分、历史记录、竞态抢占失败后的候选回退。
2. Worker dry-run 构建通过，确认代码能被打包。
3. 本地 D1 migration 和关键 SQL 的 `EXPLAIN` 通过，确认 schema、候选查询、条件抢占更新都能被 D1/SQLite 解析。

跑过的关键命令包括：

```bash
npm test
npx wrangler deploy src/worker.js --name [worker-name] --compatibility-date [date] --dry-run
npx wrangler d1 migrations apply [database-name] --local
```

最终结果：

```text

Worker dry-run passed
Local D1 migration passed
Candidate query EXPLAIN passed
Guarded claim UPDATE EXPLAIN passed
```

## Lessons

这次最有价值的提醒是：匹配系统的第一优先级不是“算法聪明”，而是“关系不能错”。

随机匹配当然粗糙，但随机本身不是最危险的；最危险的是并发下数据库关系写错。一旦用户 A、B、C 的关系被写成交叉状态，后面的问答、语音、联系方式交换都会被污染。

第二个提醒是，推荐算法不一定要一步到位。一个可解释、可测试、可降级的第一版，往往比一个听起来高级但难以验证的模型更适合早期产品。

这次的第一版算法其实很朴素：

- 真人优先
- 排除历史重复
- 简单关键词重叠
- 简单活跃时间接近
- Top N 随机探索

但它已经比纯随机多了一个重要能力：每一次匹配都能解释为什么这个人会被选出来，也能在日志和历史表里留下后续优化的入口。

后面真正值得做的，不是立刻堆复杂模型，而是继续补数据闭环：

- 匹配曝光
- 用户是否继续
- 是否听语音
- 是否交换联系方式
- 是否报名线下活动

等这些漏斗数据有了，再回头调整“喜欢”和“厌恶”的权重，才不会只是在凭感觉调参。
